## Changes and rationale

### The content revision is now read

`buildInfo` carries `contentRevision` and `contentSchemaVersion`, read at build
time from the runtime bundle. Before this, the revision `prepare:data` computes
had no reader anywhere in `src/` (audit S02), so nothing could tell one
release's content from another's.

### Anything that did not come from this build is filtered, not trusted

`validateRuntimeBundleForTarget` in `publicationPolicy.ts` runs a candidate
bundle through **the same selectors the build uses** — not a second rulebook. It
refuses a schema mismatch, a missing content revision, a bundle with no eligible
person, or unresolved references after filtering, and the refusal names the
reason.

It **filters** rather than merely inspecting. An import carrying withheld
content is reduced to what the build would have published, which is what closes
P08: a withdrawn record cannot be reinstated through an import.

The stored import is re-validated on every read rather than trusted from when it
was written, because it lives in localStorage and an artifact updated since the
import may no longer read that schema. An entry that stops passing is discarded
and logged. Reads are memoised on the raw stored string, since validation walks
a multi-megabyte bundle and sits on common render paths.

### An active import is visible and reversible

The shell shows a banner naming the imported revision and whether it matches the
build, with a control that returns to published data without reaching the
passcode form.

### The dead fallback is gone

The runtime bundle's localStorage fallback could never fire: the payload is
3,150,834 bytes against a 1,500,000-byte cap, so the write always skipped and
the read could never return (audit S03). The branch is removed with a comment
saying why, rather than left looking plausible. Offline continuity is EV-03's
job.

The remaining cache is revision-stamped, so content from a previous release is
not served, and an oversize entry now warns instead of logging at `debug` —
that silence is exactly how the bundle's fallback became unreachable.

### Staff tooling is out of the public artifact

`vite.config.ts` aliases the staff panel to a stub for the public target, so the
panel and everything it imports are absent from the bundle rather than merely
unreachable by route. The public bundle is 26 kB smaller.

### A finding worse than the audit recorded

Removing the panel exposed that `installationConfig.ts` read `import.meta.env`
by **computed key**, which defeats Vite's static replacement and inlines the
entire env object. A build setting `VITE_CIHOF_ADMIN_PASSCODE` therefore shipped
it in the public bundle whether or not the admin panel was present.

Configuration now reaches the client through an explicit allowlist built in
`vite.config.ts`. The passcode is excluded by construction rather than by hoping
the bundler drops it.

### Staff coverage moved to the artifact that has the feature

Gating the panel left two MG-tested behaviours without coverage, because the
visitor suite runs against the public build. Rather than delete the tests or
weaken them to assert absence, they now run in a new staff project against a
kiosk build on its own port and output directory.

## Existing failures versus introduced regressions

Two defects were introduced during this stage and fixed before it closed. Both
are recorded because the way they were found matters more than the fix.

The first attempt at closing the env leak read each `VITE_` key statically. A
grep over the built bundle showed the passcode was gone, and that was reported
as done — but the page was never loaded. `import.meta.env` did not survive being
referenced for undefined keys, every configuration read threw, and the app
rendered zero people. The full suite caught it: 23 of 86 passed.

The second was mine in the replacement: `configuredEnv` was declared after
`installationConfig`, which is evaluated at module load and calls the readers
immediately. In source that is a temporal dead zone error; minified it became
`undefined`. Fixed by declaring it before first use.

Both share one cause: checking an artifact instead of the behaviour. The
diagnosis that worked was loading the page and reading the console.
